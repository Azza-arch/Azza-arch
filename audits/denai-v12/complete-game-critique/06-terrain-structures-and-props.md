# 06 — Terrain, structural logic, and object placement

## A. Terrain composition

Checked directly against `environment.js`'s terrain-generation loop (`baseTerrain`, the frame-selection ternary at lines 37-40) and all 28 screenshots.

| Concern | Finding | Classification |
|---|---|---|
| Rectangular land masses | Confirmed — every `SURFACES` entry with `kind:'solid'` renders as a perfect rectangle (`s.add.rectangle` for the collider, tile-filled for the art). No slopes, no rounded transitions, no organic edges anywhere in the game. | Composition weakness, not a bug — this is simply what the terrain generator produces; it was never designed to do otherwise. |
| Repeated dirt pattern | Confirmed — the fill frame alternates only between two near-identical dirt-texture tiles (`4+((x/54+y/54)&1)`), a checkerboard dither, not genuine variety. | Composition weakness (minor — the dither does break up flat repetition somewhat, confirmed visually, it's just a very small amount of variety). |
| Vertical seam artifacts | None found in 28 screenshots at normal zoom; the terrain loop correctly computes left/right edge frames per-tile based on neighboring surface presence (`surfaceAt()`), so edges are deliberately mitred, not just cut off. | Not verified as a problem — actively verified as handled correctly. |
| Grass boundaries | Clean in every capture — top-edge frames (20/21/22/23) consistently render a grass cap over the dirt fill. | No issue. |
| Cliff silhouettes | Every "cliff" in the game is a vertical rectangle edge, never an angled or jagged one. Confirmed in R13 (F's hill) and strip-04 — even the one zone built around hill traversal uses flat vertical drops between tiers, not cliff-shaped terrain. | Composition weakness — this is the single clearest terrain-level manifestation of "repeated rectangular geometry" (the F hill *should* be the game's one organic-feeling terrain feature and isn't). |
| Floating ledges | None found that aren't intentionally supported — every oneWay deck has its own post/beam framing; A-ledge, D-service, D-rack, E-cave-walkway, F-moving-deck all have either a post frame or (for the moving platform) an explicit, visible reason (motion) for lacking one. | Not a bug. |
| Terrain edges | Correctly mitred per the `surfaceAt()` logic above. | No issue. |
| Ground-to-water transitions | Only Zone G has real water-adjacent ground. The transition (frame 33 top row over frame 73 fill) is clean at the surface line; the *depth* of the fill (7 more rows of repeating frame-73 below the surface) is still present and still a known, deliberately-deprioritized issue (confirmed again in strip-05 — visible below the crossing, not during normal play). | Composition weakness, P3 (already correctly triaged as low-priority in Phase 6.5C1/6.5C2A; this audit does not dispute that triage). |
| Terrain cut off/unsupported | None found — Phase 6.5C1 already investigated this specific question (D-service ladder running off-camera, E's pipe-as-walkway) and concluded both were intentional, not bugs; independently re-checked in this audit via the same two locations and the same conclusion holds. | Confirmed not a bug (re-verified, not re-guessed). |
| Unnatural visual repetition | See file 03/05 — confirmed at the *structural module* level (post+ladder+deck), not at the raw tile level. | Composition weakness, the central finding of this whole critique. |
| Terrain extending beyond visible boundaries | Not found — `WORLD.width=8400` is a hard bound, `BATCH_END=8400` matches, camera bounds confirmed in source (`setBounds(0,300,BATCH_END,1566-300)`) to clamp correctly; both world edges were directly screenshotted in this audit (R01/strip-01 at x≈0, R16/strip-05 at x≈8400) with no overrun visible. | No issue. |

## B. Structural support — the "does this look like it's carrying weight" audit

For every structural category the brief lists, checked against direct observation:

- **Timber decks:** Every deck (`DECKS` array, `kind:'oneWay'`) is drawn via `s.deck()`, which crops the atlas's own bridge-plank frames (48/49/50) at the correct span width — these consistently read as "a plank bridge," connected at both visible ends to a post, confirmed in every room screenshot containing one. **No dangling decks found.**
- **Wooden supports (posts):** The `post()` helper always draws a full vertical run from `top` to `bottom`, i.e., posts always visually reach the ground or another surface — confirmed, no post in any screenshot terminates in mid-air. **This is correctly handled.**
- **Ladders:** Every `LADDERS` entry draws rungs for its full `top`→`bottom` span and is paired with a real climbable zone of matching height (confirmed via `game.js`'s ladder-overlap logic, which uses the same `top`/`bottom` values). The one case flagged by a prior audit (D-service's ladder visually running off the top of the normally-framed camera view) was independently re-checked here: it is real, continues to a real platform (D-service), and is simply taller than the player usually sees at once — not a dangling or disconnected ladder.
- **Bridges (gates):** All four `GATES` are drawn via the same `s.deck()` call used for static decks, with a `parkedY` well below the visible play space when unsolved — confirmed in multiple screenshots (e.g., strip-02 shows a parked lift-gate plank floating far below the lift cluster, correctly out of the normal sightline, not visible as a "broken" object because it's simply below where the camera frames).
- **Rope/rope-like elements:** None exist in the game — no rope asset is used anywhere (confirmed via a full grep of `environment.js` for rope-related frames; none found). Not applicable.
- **Overhangs:** The only overhang-like structure is F-cave-roof (oneWay, drawn as a deck above a solid floor) — reads correctly as a cave ceiling, confirmed in R14.
- **Signposts:** Every sign (`tile(85,...)` or `tile(9,...)`) sits directly on a real surface at ground level or on a deck — none float. The one previously-flagged *crowding* case (D's two signs at x=3372/3420, 48px apart) was investigated by Phase 6.5C1 and left as a minor cosmetic note, not fixed; it remains present and is re-flagged here as still open (see file 15, issue D-SIGN-GAP).
- **The lift:** The single best-realized mechanism visually — actuator marks, lever, and selector read as one connected machine (confirmed, and further strengthened by Phase 6.5C2B's row-extension fix, independently re-verified in this audit's R05 capture).
- **Pipe supports:** E's pipe run is decorative (no physics body, confirmed via source: the `tile()` helper never calls `physics.add.existing`), suspended visually between two real posts at either end of its span — reads as "pipe resting on a rack," not as dangling, because the post+beam frame around it is real geometry.
- **Suspended platforms:** The only one is F's moving platform, which is *supposed* to be suspended (it's a moving platform) — no issue, though its lack of visual distinction from a static deck is flagged in file 04/05 as a legibility gap, not a "looks broken" issue.

**Overall finding for Part B:** The brief's fear ("does a decorative pole look like a dangling rope," "does anything hang in midair without explanation") is **not substantiated anywhere in this audit**. Every structural element that should be supported is visibly supported. The actual problem (restated from files 03/05) is not that structures look *wrong* — it's that they all look *the same*.

## C. Object placement

- **Trees:** One deliberate landmark (A) + sparse midground accents (file 05) + the two cave-adjacent bush clusters. No random scatter found — every placement traces to an explicit array literal in `environment.js` with a stated purpose in a source comment.
- **Bushes:** Confirmed used consistently as "something above the walking plane" filler at flagged empty stretches (A, B, F per Phase 6.5C1/6.5C2A/6.5C2B) — this pattern works and is not overused; file 03/05 confirm decoration density is adequate, not excessive.
- **Crates:** Two uses — the Zone A puzzle crate (functional, pushable) and the two Zone D decorative crates (Phase 6.5C2A) on D-service. Neither overlaps or confuses navigation; both sit on real supported ground.
- **Signs:** The one genuine crowding case (D, 48px gap) noted above; everywhere else sign spacing (confirmed via direct coordinate comparison across all `TERMINALS`) is ≥60px apart from any neighboring interactive prop, with the sole historical exception (G's river-select/river-lever, already radius-fixed in Phase 6.5B2-G).
- **Flags/checkpoints:** Every `CHECKPOINTS` entry sits at ground level on real terrain; none float, none sit off the main path in a confusing spot (confirmed by cross-referencing all 14 checkpoint x/feet values against their zone's `SURFACES`).
- **Collectibles:** All sit either directly on a reachable surface or float with a small bob tween above one — `spawnCollectibles()` confirms the tween is uniform (±10px, 900ms) and purely decorative, no risk of a coin reading as a platform.
- **Decorative machinery:** The lift, waterworks, and river lever are the three "machines" in the game; all three are the most visually distinct props in the game precisely because they combine multiple elements (post+lever+readout, or pipe+tank+flow) into one legible cluster — this is the model the rest of the terrain's flat modules should be learning from, not an isolated success to leave alone.

**Does every decoration earn its place?** Per the brief's own test (composition / worldbuilding / player guidance / atmosphere / mechanic communication) — yes, for nearly everything audited. The one placement that does *not* clearly earn its place is the moving platform's *lack* of a distinguishing mark (file 05) — not an extra object to remove, a missing cue to add, and even that is minor (P2).

**Recommendation for removal:** None found. This audit did not identify any prop, decoration, or structure that should be *removed* for clarity — a genuinely different conclusion from "add more detail," and one worth stating plainly since the brief explicitly asked whether anything should be removed, not only added (see file 16's "what to remove, not add" section for the one candidate found elsewhere in the game: the dead `#puzzle` dialog markup, a UI issue, not an environment-art one).
